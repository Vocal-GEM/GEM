## YYYY-MM-DD - [MEDIUM] Fix Information Leakage in Error Responses
**Vulnerability:** API endpoints (`backend/app/routes/tts.py` and `backend/app/routes/voice_quality.py`) were returning raw Exception error details (`str(e)`) to the frontend inside HTTP 500/502 JSON responses. This exposes internal application state, library versions, and potential infrastructure details to clients.
**Learning:** Returning `str(e)` directly inside `jsonify` for unhandled exceptions is an information leakage risk. Furthermore, when replacing these responses with generic errors, the actual exception must still be logged server-side (e.g., using `current_app.logger.error`). Completely removing the exception without logging it creates a maintainability regression by swallowing the error. We must also be careful with string escaping inside f-strings for logger calls to avoid `SyntaxError`s.
**Prevention:** Always log exceptions server-side using an application logger, and return a sanitized, generic error message (e.g., "An internal error occurred") to the client.
